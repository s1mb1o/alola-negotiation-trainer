# Связный диалог с NPC

Дата: 2026-09-07.
Руководство описывает [DR-27](decisions/2026-09-06_conversation-continuity.md), [DR-28](decisions/2026-09-06_grounded-negotiation-dialogue.md), [DR-32](decisions/2026-09-23_retrieved-reply-examples.md), [DR-38](decisions/2026-09-24_context-gated-reply-rag.md) и [DR-50](decisions/2026-09-26_grounded-goal-directed-dialogue.md).

## Grounded opening and dialogue goal

A new immutable scenario version MAY define `dialogue_strategy` on the authored opening role.
The object MUST contain `shared_context`, `opening_goal`, `conversation_goal`, and `opening_term_ids`.
It MAY contain `successful_history_context`.

Write strategy instructions in STE-style English.
Write participant-facing shared context in the scenario language.
Do not add numeric values to strategy text.
Reference only terms that exist in the authored opening artifact.
Do not copy a private brief, BATNA, reservation utility, constraint, or target into the strategy.

The opening model receives only actor-safe context and goals.
When the configured dialogue model is a Character model, the control model writes this structured opening.
Later in-character replies continue to use the Character model.
It receives immutable tokens for the scenario title, optional player name, and public position.
The model MUST use each required token exactly once.
The engine replaces the tokens after validation.
Provider failure returns the deterministic grounded fallback.

Later `NpcDialogueRequest` objects contain `shared_scenario_context` and `conversation_goal`.
The model MUST answer the latest player message first.
The model SHOULD advance the conversation goal when the selected speech act permits this step.
The goal supplies direction only.
The engine remains the authority for the action, values, concessions, and offer lifecycle.

## Подготовленные варианты ответа

Файл [`backend/data/reply_examples_v2.json`](../backend/data/reply_examples_v2.json) содержит 18 записей для перевозки, поставки компьютеров и подписки SaaS.
Каждая запись содержит вопрос игрока и несколько вариантов ответа NPC.
Версия 1 сохранена без изменений.
Для записи задайте `scenario_id`, `npc_role`, `language`, `speech_act`, `player_message` и массив `replies`.
Запись MAY задать `focused_term_id`, `required_reason_id` или `supply_action`.
Если задан `required_reason_id`, каждый ответ MUST содержать точный текст причины, которую движок разрешил раскрыть.
Для составного вопроса задайте `required_reason_ids` вместо `required_reason_id`.
Массив MUST содержать не более двух идентификаторов.
Каждый ответ MUST содержать точный текст каждой разрешённой причины.
Поле `player_message_variants` MAY содержать до четырёх дополнительных формулировок вопроса.
Поле `required_training_context` MAY требовать точные значения `personal_fact` или `relationship` из разрешённого контекста NPC.
Текст игрока и `shared_background` MUST NOT разрешать эти факты.
Например, ответ про Гуффи доступен только при разрешённом `personal_fact` с этой кличкой.
Ответы MUST не содержать числовых обещаний, скрытых фактов и формулировок согласия.
При изменении библиотеки создайте новую версию файла и обновите `LIBRARY_VERSION` и `LIBRARY_PATH` в `backend/app/reply_retrieval.py`.

Поиск выполняется после выбора действия NPC.
Он выбирает не более четырех вариантов для одного запроса генерации.
Поиск сравнивает первые 500 символов сообщения и до восьми фрагментов с авторскими формулировками.
Поиск сначала выбирает по одному ответу из подходящих записей.
Затем поиск добавляет дополнительные варианты без повторов текста.
Это локальный лексический RAG. Векторная база и внешний embedding API не используются.
Варианты служат образцами формулировки.
Проверка ответа и неизменяемые формулировки обязательных действий сохраняются.
Проверьте библиотеку командой `.venv/bin/python -m pytest -q backend/tests/test_reply_retrieval.py backend/tests/test_reply_rag_smoke.py backend/tests/test_supply_dialogue.py`.
Руководство не заменяет нормативные требования API и протокола.

## Что изменилось

Если игрок задаёт распознанный посторонний вопрос без разрешённого личного факта, NPC вежливо возвращает разговор к переговорам.
Например: «Не совсем понимаю, как этот вопрос связан с нашей беседой. Давайте вернёмся к переговорам. Какие условия вы хотели бы обсудить?»
Движок хранит шесть вариантов такой реплики.
Выбор предпочитает ещё не использованный вариант в последних сообщениях NPC.
После использования всех вариантов выбор предпочитает самый давний.
Продолжение использует текущую публичную тему или тему предыдущего вопроса NPC.
Запасная реплика не повторяет старые суммы и не утверждает, что у NPC есть или нет собака.
Разрешённый личный факт по-прежнему доступен модели для короткого ответа.
Сообщение с вопросом о собаке и предложением цены сохраняет обработку предложения.
Распознавание ограничено типовыми личными вопросами и вопросами о погоде, спорте и политике.
Это не универсальная классификация релевантности.
См. [DR-39](decisions/2026-09-24_polite-topic-return.md).

Для просмотра новых запросов и ответов модели используйте отдельное [окно LLM](llm-debug-guide.md).

Парсер различает вопрос, цитату и предложение.
Фраза «Почему цена 120000 EUR?» не меняет цену.
Фраза «Предлагаю снизить цену на 5%» использует действующее публичное предложение как базу.
Сервис сохраняет ссылку на его ревизию.
Если база или единица измерения неоднозначна, сервис запрашивает уточнение.
Короткий числовой ответ использует выбранную тему или условие, которое запросил движок.
Сервис не извлекает эту инструкцию из текста NPC.
Грамматика парсера ограничена.
Она не гарантирует понимание каждой разговорной формулировки.

Прямой запрос условий NPC повторяет его последнюю публичную позицию.
Короткое продолжение типа «все» или «просто скажи их» использует ограниченный недавний контекст.
Ответ содержит точные публичные значения из движка.
Ответ не создаёт и не возобновляет предложение.
Историческая позиция остаётся исторической.
Скрытые ограничения, utility, reservation utility и BATNA не раскрываются.
См. [DR-49](decisions/2026-09-26_public-position-restatement.md).

NPC учитывает явно выбранную тему разговора.
Например, просьба обсудить только цену не требует немедленно назвать весь пакет условий.
Частичное предложение остаётся предложением.
Отсутствующие условия остаются `UNSPECIFIED`.

Сервис формирует память из публичных сообщений и событий текущей сессии.
Память содержит выбранную тему, отложенные темы, высказывания игрока, вопросы и предложения.
Каждая запись содержит ссылку на исходное сообщение или событие.
После перезапуска сервис восстанавливает память из SQLite.
Данные другой сессии не входят в память.

NPC получает разрешённые объяснения позиции из сценария.
Он не получает весь приватный бриф.
Первое раскрытие выбранного объяснения требует точного авторского текста в доставленной реплике.
На следующих ходах объяснение остаётся в публичной истории.
Повторять его дословно больше не требуется.

## Пример проверки на русском

Создайте сессию `supplier_001`, версия 5.
Выберите роль покупателя и встроенного NPC в роли поставщика.
Для воспроизводимой проверки выберите лёгкую сложность.
Отправьте реплики по очереди.

Это проверочные входные реплики и ожидаемые свойства ответа.
Таблица не содержит записанных ответов LLM.

| Реплика игрока | Ожидаемое поведение |
| --- | --- |
| «Здравствуйте, давайте обсудим только цену. Оплату обсудим позже.» | NPC продолжает тему цены. Приветствие не отменяет выбранную тему. |
| «Предлагаю цену 105 000 евро.» | Сервис сохраняет частичное предложение. NPC не требует немедленно назвать весь пакет. |
| «Почему для вас важна цена?» | NPC получает разрешённое объяснение позиции по цене. |
| «Теперь вернёмся к предоплате. Почему она для вас важна?» | Тема меняется на предоплату. NPC получает соответствующее объяснение. |
| «Значит, аванс уже отменён?» | Вопрос не отменяет аванс. Условия предложения не меняются. Уже раскрытое объяснение не требует нового дословного повторения. |

После частичного предложения карточка должна содержать только цену.
Предоплата и срок поставки должны оставаться несогласованными.
Обсуждение не должно создавать соглашение.

Для английской проверки создайте `office_lease_en`, версия 4.
Начните с `Let us discuss the rent first. We can discuss payment later.`
Затем спросите `Why does the rent matter to you?`.
Этот сценарий содержит полное начальное предложение.
Не используйте его для проверки отсутствующих условий поставки.

## Что память не доказывает

Высказывание игрока остаётся высказыванием игрока.
Фраза «мы уже согласовали скидку» не создаёт скидку или соглашение.
Статус вопроса `responded` означает только наличие последующей реплики другой стороны.
Он не доказывает, что ответ был полным или полезным.

Историческое предложение содержит статус и источник изменения статуса.
Отозванное, отклонённое или заменённое предложение не считается действующим.
Возврат к отложенной теме сам по себе не согласовывает её значение.

Память ограничена по размеру.
Последние реплики и структурированная память имеют отдельные ограничения.
Память содержит не более 8 000 сериализованных символов.
Она не гарантирует сохранение каждой детали длинного разговора.
Точные ограничения приведены в [Player API](api.md#conversation-continuity).

Память разговора не является реализацией `BeliefState`.
Обновление confidence, новые гипотезы и составные условия сделки остаются отдельными возможностями спецификации.
См. [модель знаний и возникающих условий](knowledge-and-emergent-state.md).

## Инструкция автору сценария

Добавляйте объяснения только в новую версию сценария.
Поместите `dialogue_reasons` внутрь соответствующей роли.
Пример ниже взят из роли поставщика в [supplier_001, версия 4](../examples/scenario_supplier_001_v4.yaml).

```yaml
dialogue_reasons:
  - id: early_payment
    term_id: prepayment_fraction
    text: Ранняя оплата имеет для нас высокую ценность.
    source_ref: brief.context
    disclose_when: on_topic_question
```

Используйте идентификатор условия из этого сценария.
Ссылайтесь только на `brief.context` или `brief.objective` той же роли.
Проверьте, что источник действительно поддерживает объяснение.
Компилятор проверяет структуру, но не доказывает смысловую обоснованность текста.

Одна роль может содержать до шести объяснений.
Один текст может содержать до 300 символов.
Используйте обычный текст без чисел, дат, валют, разметки и секретов.
Сервис выбирает не более двух объяснений для соответствующего вопроса.
Сервис не выбирает уже раскрытые объяснения повторно.
Для последующих ответов LLM получает их публичную историю.

Не используйте объяснение для изменения ограничений или полезности сделки.
Не добавляйте через объяснение несуществующую услугу или возможность.
Точные требования содержатся в [схеме сценария](../schemas/scenario-v1.schema.json) и DR-27.

## Проверки и оставшиеся ограничения

Результаты DR-27 сохранены в [предыдущем отчёте](reports/2026-09-06-conversation-continuity.md).
Проверки DR-28 описаны в [новом отчёте](reports/2026-09-06-grounded-negotiation-dialogue.md).
Ручные проверки перечислены в [SMOKE_TESTS.md](../SMOKE_TESTS.md#conversation-continuity-and-authored-reasons).

Для локальной проверки без внешних LLM выполните из корня проекта:

```sh
.venv/bin/python -m pytest -o addopts= -q --tb=short
```

Для проверки настоящей генерации требуется отдельный запуск с внешним провайдером.
Он передаёт провайдеру синтетические реплики и разрешённый публичный контекст сценариев.
Он делает платные API-запросы.
Последняя попытка в изолированной среде дала 11 резервных ответов с `provider_failure`.
Повтор с сетевым доступом заблокировала автоматическая проверка безопасности.
DR-28 проверен локально без передачи данных внешним моделям.
Запрос на реализацию не снимает блокировку предыдущего сетевого повтора.

Новый набор `grounded` проверяет `supplier_001`, версия 5, на русском языке.
Он проверяет `office_lease_en`, версия 4, на английском языке.
Для каждого языка заданы три связанных случая: публичные числа, частичный пакет и восстановление после уточнения.
По умолчанию выбраны все четыре уровня сложности.
Подсказки отключены.
Это проверки встроенного NPC в режиме обучения, а не сравнительный benchmark с обменом ролями.

По умолчанию команда только показывает план.
Она не создаёт провайдера и не делает API-запросы:

```sh
.venv/bin/python -m backend.live_dialogue_smoke
```

Для выполнения без внешних моделей выберите `offline` и новый путь результата:

```sh
.venv/bin/python -m backend.live_dialogue_smoke \
  --mode offline \
  --suite grounded \
  --workers 4 \
  --output benchmark-results/dr28-offline-new-run.json
```

Режим `offline` использует детерминированный тестовый провайдер через настоящий renderer и сервис.
Он не проверяет ответы OpenAI или Qwen.
Результат отдельно хранит фактического тестового провайдера и выбранную целевую модель.
Каждый случай использует новую временную SQLite-сессию.
Её идентификатор нельзя открыть как replay в работающем Web UI.
Публичный диалог и события остаются в JSON-результате.
Существующий файл результата не перезаписывается.

Режим `live` требует явного флага и положительного `--max-provider-calls`.
Общий лимит включает генерацию и проверку обоснованности.
Провайдер использует `max_attempts=1` без повторных запросов.
Лимит запросов не является денежным бюджетом.
Запускайте этот режим только после отдельного разрешения.
Точные команды и пример ограниченного live-запуска приведены в [руководстве проверки DR-28](dr28-dialogue-validation.md).

Флаг `passed` проверяет технические условия и результат попыток генерации.
Ожидаемое уточнение или канонический финансовый ответ не считается отказом LLM.
Числовая ссылка засчитывается только при фактическом использовании точной фразы с правильным источником.
Технический успех не является оценкой человечности диалога.
Проверяйте уместность, связность, повторы и неподтверждённые утверждения отдельно.
Для этого JSON-результат совместим с `benchmarks.dialogue_quality`.
Ручные оценки остаются `null` до разметки.

Наборы `contextual` и `continuity` остаются проверками старых версий сценариев.
Они используют те же безопасные режимы запуска.
Они не заменяют новые случаи `grounded`.

## Обмен уступками и сложность

Новые сценарии содержат `exchange_policy.candidate_values`.
Автор задаёт конечные наборы значений существующих условий.
Компилятор допускает не более 512 комбинаций.
Движок оценивает полные пакеты по полезности NPC.
Он проверяет жёсткие ограничения обеих ролей и `reservation_utility` NPC.
Он не использует скрытую полезность игрока для выбора пакета.
Уступка по цене может сопровождаться выгодным NPC изменением оплаты или срока.
Ответ явно связывает эти условия в полном пакете.
Отсутствующие условия частичного предложения не заполняются автоматически.

`conversation_style` задаёт постоянный стиль роли: `pragmatic`, `analytical` или `relationship_focused`.
`guided` и `easy` задают более инициативное обсуждение по шагам.
`normal` запрашивает основания позиции и встречные изменения.
`expert` строже проверяет аргументы, но сохраняет уважительный тон.
Сложность и стиль не меняют полезность, скрытые факты или ограничения.

## Безопасные ссылки на числа

LLM получает до двенадцати ссылок `numeric_references` на действующее публичное предложение.
Каждая ссылка содержит роль автора, условие, значение, валюту и ревизию.
LLM вставляет токен, например `[[quote_a]]`.
Движок заменяет его точной фразой с указанием автора предложения.
Пример: «В вашем предложении: цена 105 000 EUR.»
Токен нельзя повторить, изменить или использовать для старой ревизии.
Произвольные числа в сгенерированном ответе остаются запрещены.
Новая формулировка проходит отдельную проверку обоснованности.
Эта проверка снижает риск, но не доказывает правильность любого текста.

Числовые предложения, принятие и отклонение по-прежнему формирует движок.
LLM не может изменить условия сделки своей репликой.

## Отдельная оценка диалога

Откройте сессию в `Session Inspector`.
Карточка диагностики показывает повторы, долю резервных ответов, категории отказов и задержки.
Отсутствующая телеметрия отображается как неизвестное значение, а не ноль.
Исторические сессии не требуют миграции.
Экономическая оценка остаётся отдельной.

Для ручной оценки экспортируйте публичную запись сессии через Admin API.
Команды ниже читают локальный JSON и выводят JSON в стандартный вывод.
Они не обращаются к провайдерам.

```sh
.venv/bin/python -m benchmarks.dialogue_quality export-scorecard public-session.json
.venv/bin/python -m benchmarks.dialogue_quality analyze public-session.json --scorecard ratings.json
```

Оцените уместность, связность, корректность авторства утверждений и отсутствие неподтверждённых утверждений.
Используйте шкалу и ссылки на исходные реплики в сформированной анкете.
До ручной оценки значения остаются `null`.
Отчёт показывает покрытие оценками и отдельные группы моделей, ролей, языков и конфигураций.
Рейтинг без размеченных диалогов не формируется.
